# psort Single-Worker Performance — IDENTIFY-Phase Report

**Scope:** The single-threaded output / sort / format / write stage of upstream `log2timeline/plaso` (`plaso/multi_process/output_engine.py`, entry `ExportEvents`, driven by `plaso/cli/psort_tool.py`), plus its storage dependency `acstore`. Analysis only — no code changes proposed.

**Codebase confirmed:** Upstream `log2timeline/plaso` + `acstore` (verified in `/home/user/log2timeline/plaso` and `/home/user/log2timeline/acstore`). The checkout at `/home/user/plaso` is the `Get-Sybers` fork and is **not** the subject of this report. All line citations below were spot-checked against upstream: the zlib blob path (`sqlite_file.py:88-104`), `order_by="timestamp"` (`sqlite_file.py:451` → acstore `sqlite_store.py:470`), the lone `event_tag_per_event` index (`sqlite_file.py:135`), the per-event literal-rowid query (`sqlite_file.py:356-363`), the 32K LRU (`acstore/interface.py:236,250-255`), and the read-only pragma block (`acstore/sqlite_store.py:1018,1039,1042`).

---

## 1. Executive summary

psort's cost at realistic scale (100k–10M events) is overwhelmingly **per-event work on one CPU core**. The export loop walks events in timestamp order and, for *every* event, issues a single-row SQL lookup of a zlib-compressed JSON `event_data` blob, decompresses it, JSON-parses it, and rebuilds a Python container — then formats and writes it. This per-event decode is the dominant, unconditional cost of every run and is paid for all 22 output modules identically. A one-time, un-indexed full-table `ORDER BY timestamp` sort sits in front of it, and when analysis plugins are enabled the entire sort-plus-decode is performed **twice** end-to-end.

The nine perspectives converge on a small number of root causes. Adversarial verification trimmed the original "critical" labels: SQLite is in-process (so "N round-trips" are not network hops), and a 32K-entry LRU read cache already absorbs *repeated* references to the same `event_data`. What survives as genuinely high-leverage is (a) the per-event blob **decompress + JSON decode + object rebuild**, (b) the fact that it runs **single-threaded** while being embarrassingly parallel, (c) the **un-indexed sort**, and (d) the **double pass** under analysis plugins.

Two tiers of remedy emerge. **Cheap/safe wins** — a persisted `event(timestamp)` index, read-oriented PRAGMAs, parameter binding, promoting the dedup key to an event-table column, per-event memoization of formatter/datetime work — shave real time with low risk and preserve byte-identical output. **Larger re-architecture** — a single ordered `event ⋈ event_data` streaming JOIN, and a producer/consumer pipeline that parallelizes decode+format ahead of a serial deterministic sort/dedup/write tail — is where the order-of-magnitude headroom is, since the hot work releases the GIL (zlib, SQLite) or is pure per-event computation.

## 3. The 3–5 highest-leverage opportunities

1. **Collapse the per-event `event_data` N+1 into one ordered stream (#1).** This is the most-corroborated finding (6 perspectives) and the dominant unconditional per-event cost. Direction: drive `event_data` reads by an ordered `event ⋈ event_data` JOIN (optionally `LEFT JOIN event_data_stream`) in the sorted scan, replacing N random `WHERE rowid = N` probes with one sequential cursor. The zlib+JSON decode still runs per surviving row, but the random-access SQL and B-tree re-descents disappear and locality is restored — which also makes the 32K LRU irrelevant rather than a bottleneck.

2. **Parallelize decode+format behind a serial deterministic tail (#2).** The decompress/JSON-decode and message formatting are pure functions of the input bytes/container and independent across events; zlib and SQLite C calls release the GIL. Direction: a worker pool (thread pool first — it exploits the GIL-releasing zlib/SQLite paths with no pickling cost; escalate to a process pool for the Python-bound JSON/format work) decodes+formats out of order, each result tagged `(timestamp, insertion index)`; one consumer reassembles in deterministic order into the existing `PsortEventHeap` so sort/dedup/MACB/write stay serial and byte-identical. The engine already subclasses `MultiProcessEngine` and the extraction side already ships a working worker-pool-with-merge pattern.

3. **Persist the sort order with a `event(timestamp)` index (#3).** The single cheapest high-value safe win. Direction: build an index (ideally covering `(timestamp, _identifier, _event_data_identifier, timestamp_desc)`) once at storage-finalization time so psort replaces the full external sort with an ordered index scan, eliminating the O(N log N) sort and the pre-first-row stall, and turning `--time-slice` into an indexed range seek. Amortized across every later re-export.

4. **Stop doing everything twice under analysis plugins (#4).** When ≥1 analysis plugin is enabled, the analysis pass and the export pass each run an independent full `ORDER BY timestamp` sort plus N blob decodes over the same store with no shared cache. Direction: fan one ordered scan to both the plugin consumers and the export formatter, so the sort and the `event_data` materialization happen once.

5. **Move the dedup key out of the compressed blob (#5).** The dedup key `_event_values_hash` lives inside `event_data`, so every duplicate is fully decompressed+parsed before it can be discarded. Direction: promote `_event_values_hash` (and `timestamp_desc`, already an event column) to first-class event-table columns so duplicate suppression is a cheap row comparison *before* blob hydration — decode then scales with surviving events, not all events. Impact scales with duplicate rate (low for single-source runs, large for re-processing / VSS-overlapping / multi-parser corpora).

## 4. Themed findings

### Theme A — Storage & I/O

**A1 (opportunity #3). No index on `event.timestamp`; full external sort every run.**
`GetSortedEvents` issues `SELECT _identifier, <cols> FROM event ORDER BY timestamp` (`plaso/storage/sqlite/sqlite_file.py:447-451` → acstore `sqlite_store.py:463-470`). The only index in the store is `event_tag_per_event` on `event_tag(_event_identifier)` (`sqlite_file.py:135`); there is **no** index on `event.timestamp`. SQLite therefore builds a transient B-tree / external merge sort over the whole event table and must fully materialize it before yielding the first row (acstore `sqlite_store.py:487` `fetchone`). Runs once-per-run; O(N log N); spills to file-backed temp under default `temp_store`. Verified CONFIRMED by three perspectives; severity corrected from critical→high / high→medium because it is a one-time cost and the per-event loop (A2) dominates total throughput — but it is the single cheapest high-value safe win, and the "first row blocks until the full sort completes" sub-claim is correct. The ordered SELECT also projects the full (narrow) event row — `_identifier, _event_data_identifier, date_time, timestamp, timestamp_desc` (`events.py:373-378`) — so the sorter carries five columns including the TEXT `date_time`; a covering index removes both the sort and the row materialization. **Affects: all output types** (upstream of the output module). **Direction:** persisted `event(timestamp)` / covering index at finalize time; or at minimum `temp_store=MEMORY` + larger page cache. **Caveat:** chronological ordering is a semantic requirement; the index shifts the cost to write time, it does not remove ordering.

**A2 (opportunity #1). Per-event random-access `event_data` blob fetch + decode.**
See Theme C (C1) — this is primarily a per-event CPU/decode cost; the storage angle is that the reads are *random* (A3) and un-batched.

**A3. Timestamp-order iteration vs insertion-order rowids thrashes the 32K LRU and page cache.** CONFIRMED (storage-io, high). Events are yielded in timestamp order but each event's `event_data` is fetched by rowid, and `event_data` rowids follow insertion order (`acstore sqlite_store.py:866-868` → `GetAttributeContainerByIndex(sequence_number - 1)`). The reference stream is effectively uniform-random over the whole table. The read cache is an `OrderedDict` LRU capped at `32 * 1024` (`acstore/interface.py:236,243-271`, verified). Once distinct `event_data` exceeds ~32K the hit rate collapses toward `cache_size / working_set` and nearly every event is a cold single-row read into a random B-tree page. **Affects: all.** **Direction:** drive blob reads by physical order (the ordered JOIN of C1) so the stream becomes sequential and a small cache suffices; if a cache is kept, size it to the real MACB/same-timestamp locality rather than a fixed 32K.

**A4 (opportunity #6). Read connection lacks `cache_size` / `mmap_size` / `temp_store` tuning.** PLAUSIBLE (storage-io + native-sqlite, medium). `Open()` sets only `PRAGMA journal_mode=MEMORY` and `synchronous=OFF` (`acstore/sqlite_store.py:1039,1042`, verified), both write/durability knobs that are **inert on the `?mode=ro` read connection** (`:1018`). No `cache_size`, `mmap_size`, or `temp_store`. The two cost centers (the external sort in A1 and the random blob reads in A3) therefore run against SQLite's ~2MB default page cache and file-backed temp. **Affects: all.** **Direction:** on the read connection set `temp_store=MEMORY`, a large negative `cache_size`, and `mmap_size` to memory-map the store. Partially mitigated by the app-level 32K LRU and OS page cache, so benefit is moderate/uncertain; largely subsumed once A1's index removes the sort spill.

**A5 (opportunity #13). Literal-rowid f-string queries defeat the prepared-statement cache.** CONFIRMED (storage-io + native-sqlite, corrected to low). `sqlite_file.py:356-363` builds `... WHERE rowid = {row_number:d}` as a new SQL string per event (verified) and `cursor.execute`s it; acstore `sqlite_store.py:900-908` is the same pattern for `event_data_stream`. Distinct SQL text per call ⇒ guaranteed statement-cache miss ⇒ re-parse/re-plan each of the N lookups. **Affects: all.** **Direction:** bind the rowid as a parameter (`WHERE rowid = ?`). Standalone impact is minor (it does not remove the round-trip); moot once C1's JOIN replaces per-event lookups.

**A6. `_CommitWriteCache` on the read path — verified non-issue.** PLAUSIBLE/low. Called per lookup (`sqlite_file.py:349`, acstore `sqlite_store.py:458,888`) but in read-only mode the write cache is always empty, so the body is a `dict.get` + a `len(...) > 1` comparison with no SQL. Reported only for completeness; not a hotspot.

### Theme B — Sorting & Deduplication

**B1 (opportunity #5). Dedup/MACB key lives inside the compressed `event_data` blob.** CONFIRMED (sort-dedup, high; corroborated by cpu-hotspots medium, orchestration low). The dedup key is `_event_values_hash`, an attribute of `EventData` (`events.py:236`); the event table (`events.py:373-378`) carries `timestamp`/`timestamp_desc` but **not** the hash. The export loop fetches+decodes `event_data` for every event (`output_engine.py:278`) and reads the hash via `getattr(event_data, "_event_values_hash")` (`output_engine.py:86`); dedup (`output_engine.py:424-430`) and MACB keying (`:441`) only run at flush, *after* hydration. So every duplicate pays the full SQL + decode before being dropped (`:429 continue`). **Affects: all** for the dedup compute (engine-level, `deduplicate_events` defaults True; `-a`/`--include-all` disables); the MACB *output* effect is l2t_csv-only (base `WriteFieldValuesOfMACBGroup` writes each event individually). **Direction:** promote `_event_values_hash` (and `timestamp_desc`) to event-table columns so same-timestamp dedup runs before blob hydration; hydrate only survivors. The genuinely wasted work is decode of *distinct duplicate rows* (same hash, different rows) — the 32K LRU covers MACB siblings that share one `event_data` row but not true duplicates. Impact proportional to duplicate rate.

**B2. `_HEAP_MAXIMUM_EVENTS` mid-timestamp flush splits a same-timestamp group.** PLAUSIBLE, corrected to low — **a correctness defect, not a speed cost.** `_ExportEvent` flushes when `event.timestamp != _export_event_timestamp` **or** heap size > 100000 (`output_engine.py:209-212`, `_HEAP_MAXIMUM_EVENTS=100000` at `:118`). Dedup (`:424-430`) and MACB clustering (`:435-474`) are adjacency-only within one flush pass; cross-flush tail-state is not carried (`:410-413` re-init each flush). If one timestamp carries >100k events, the group is flushed in multiple independently-sorted passes, so a duplicate (or MACB sibling) across the boundary is never adjacent to its partner → duplicate emitted / MACB group split (the split is visible only in l2t_csv). Rare (needs >100k events at one identical timestamp). **Caveat for any speed change:** a streaming-dedup redesign must not re-introduce or worsen this; ideally fix it by carrying tail-state or never flushing mid-group.

**B3. heapq secondary sort compares raw tuples (invokes `EventObject.__lt__`, 32-char md5 hex compares).** PLAUSIBLE, corrected to low. The per-timestamp heap tuple is `(event_values_hash, timestamp_desc, event, event_data, event_data_stream, event_tag)` (`output_engine.py:99-109`); comparisons start on the 32-char md5 hex hash (`events.py:115-117`), then `timestamp_desc`, then fall to `EventObject.__lt__` (`events.py:392-406`, effectively vestigial within a group). Since the group is fully materialized before draining, an incremental heap buys nothing. **Affects: all** (engine-level). **Direction:** a plain `list.sort(key=...)` with a precomputed key tuple (hash, timestamp_desc, monotonic counter) runs at C level and never calls `__lt__`; comparing a fixed-width int / raw 16-byte digest instead of a hex string is cheaper. Low because the common one-event-per-timestamp case has a size-1 heap.

**B4. `timestamp_desc` recomputed in the Python heap instead of pushed into SQL `ORDER BY`.** PLAUSIBLE, low. `order_by="timestamp"` only (`sqlite_file.py:451`); `timestamp_desc` is an event column that SQLite could order by in the same sort. **No standalone benefit**, though: the heap's *primary* key is `_event_values_hash` (an `EventData` attribute SQL cannot sort by), so the heap must remain to cluster each group for adjacency dedup and would re-impose `timestamp_desc` anyway. Only valuable bundled with B1 (hash as an event column) to eliminate the heap entirely.

**B5. Clustering rebuilt in RAM every run.** PLAUSIBLE, low. `event_values_hash` is computed once at extraction (`mediator.py:530`) and persisted, so the md5 is **not** re-computed per run (already mitigated). What repeats each run is only a per-timestamp-group heap sort + an O(n) adjacency scan — modest. The "can only begin after decompressing all event_data" justification is largely invalid because output formatting needs `event_data` regardless.

### Theme C — Per-event CPU & decode

**C1 (opportunity #1, THE headline per-event cost). zlib decompress + json.loads + object rebuild of `event_data`, once per event.** CONFIRMED (cpu-hotspots high; corroborated by storage-io, native-sqlite, orchestration, memory, concurrency — 6 perspectives). For each event: `GetAttributeContainerByIdentifier(EventData)` (`output_engine.py:278`) → on cache miss `SELECT _data FROM event_data WHERE rowid=N` (`sqlite_file.py:356-361`) → `zlib.decompress` (`sqlite_file.py:90`, verified) → `decode("utf-8")` + `json.loads` (`json_serializer.py:521`) → `_ConvertJSONToAttributeContainer` rebuilds the object attribute-by-attribute via setattr (`json_serializer.py:165-187`). `event_data` is the **only** container stored as a compressed JSON blob (`sqlite_file.py:83,117-127`). At 1M–10M events this is 1M–10M decompress+parse+rebuild cycles with heavy transient allocation, single-threaded. **Affects: all output types** — the fetch is unconditional, before any output module. Severity corrected critical→high: it is the dominant per-event CPU cost, but "majority of wall-clock" was unprofiled, and `event_data_stream` does **not** take this path (it has a fixed SCHEMA and uses the cheap columnar path, and is heavily shared so the LRU absorbs it — only `event_data` is zlib+JSON). The 32K LRU is an index-keyed cache that mostly misses under timestamp-ordered access to distinct `event_data`, so it is only a partial mitigation. **Direction:** ordered streaming JOIN / batched range fetch to remove the random SQL + B-tree re-descent (A3, A5); the decode itself is inherent to the representation, so the larger win is parallelizing it (opportunity #2, Theme F) and/or a representation not requiring a full JSON reparse-into-dict-then-object.

**C2 (opportunity #10). Message-formatter resolution + full `CopyToDict` rebuild per event.** CONFIRMED (output-modules; corroborated cpu-hotspots/formatting-mediator/memory). `_FormatMessage` calls `GetMessageFormatter(data_type)` which lowercases `data_type` and does a dict.get every call (`mediator.py:323-324`), then `event_data.CopyToDict()` (a fresh dict of all attributes, `formatting_helper.py:332`), then `FormatEventValues` (iterates every helper, `interface.py:285-293`), then `GetMessage` (`str.format(**event_values)`). **Affects:** all message-bearing modules — dynamic, l2t_csv, tln/l2ttln, xlsx, json/json_line, opensearch/opensearch_ts; **not** rawpy, kml, null. Corrected high→medium: the avoidable part (`.lower()` + one dict alloc) is a constant overhead on top of the genuinely unavoidable `str.format` + helper pass. **Direction:** cache the resolved formatter per data_type; build `event_values` once per event and reuse across message/message_short/source callbacks within one `GetFieldValues`.

**C3. Unconditional `date_time` dfdatetime JSON deserialization per event.** PLAUSIBLE, corrected to low/medium. `GetSortedEvents` projects all event columns and `_CreateAttributeContainerFromRow` runs `json.loads` + `ConvertDictToDateTimeValues` for `date_time` on every event (`sqlite_file.py:432-433`, acstore `sqlite_store.py:143-148`, `serializers.py:23`). Events use the generator path (not by-index), so this is **never cached**. **Scope corrected:** genuinely wasted only for rawpy, shared_opensearch, null (they rebuild from the integer `event.timestamp` — `rawpy.py:130`, `shared_opensearch.py:64`); tln, l2t_csv, dynamic, json_out **do** consume `event.date_time` (`tln.py:101`, `l2t_csv.py:146`, `formatting_helper.py:80-96`), so for them it is required work. **Direction:** deserialize `date_time` lazily / project only needed columns for the sort path.

**C4 (opportunity #15). Cache-key f-string + `move_to_end` bookkeeping per lookup.** PLAUSIBLE, low. `_GetCachedAttributeContainer` builds `f"{container_type}.{index}"` every call (`acstore/interface.py:267`) and `move_to_end` on a hit (`:270`); the store path builds a second f-string (`:253`) + `move_to_end` (`:255`). Corrected: ~1–2 f-strings per event (not "N–10N"), trivial next to the SELECT + deserialize on a miss. **Affects: all.** **Direction:** key the cache by the native `(container_type, index)` tuple/int to drop the string allocation.

**C5 (opportunity #14). `_GetEventTag` builds a `CopyToString` key per event even with zero tags.** CONFIRMED, low. `output_engine.py:502` evaluates `event.GetIdentifier().CopyToString()` (an f-string, `acstore/containers/interface.py:42-43`) unconditionally before the dict.get, even when `self._event_tags == {}`. The tag *dict* is already cached once (`:496-500`); only the per-event key string is unmitigated. **Affects: all.** **Direction:** short-circuit when no `event_tag` containers exist; key the dict by the integer sequence number.

### Theme D — Message formatting

**D1 (opportunity #8). l2t_csv formats the message twice per event (`desc` + `short`).** CONFIRMED by three perspectives (output-modules high; cpu-hotspots/formatting-mediator medium). `_FIELD_NAMES` contains both `short`→`_FormatMessageShort` and `desc`→`_FormatMessage` (`l2t_csv.py:75,83,304-305`); `DSVEventFormattingHelper.GetFieldValues` iterates all fields (`shared_dsv.py:80-88`), so each event pays two independent `CopyToDict` + `FormatEventValues` passes, and `GetMessageShort` re-runs the full conditional assembly before an 80-char truncation (`interface.py:593-599`). **Affects: l2t_csv by default**; dynamic/DSV only if a user adds `message_short` alongside `message` (`dynamic.py:153-162` default has `message` only); json/tln/xlsx emit one message. Corrected high→medium (output-modules keeps high). **Direction:** render the long message once (one `CopyToDict` + one `FormatEventValues`) and derive the short form from it.

**D2 (opportunity #9). Per-event pytz timezone conversion repeated per time field.** CONFIRMED (formatting-mediator high; cpu-hotspots/output-modules medium). Each time-bearing field independently calls `date_time.GetDateWithTimeOfDay()`, builds a `datetime(...tzinfo=pytz.UTC)`, and converts (`_FormatDate`/`_FormatTime` via `.astimezone`, `_FormatTimeZone` via `.tzname`) — `formatting_helper.py:103-131,458-482,506-518`, `l2t_csv.py:157-169`, `dynamic.py:80-92`. pytz `DstTzInfo` does a bisect over transition times and allocates per call. **Scope:** l2tcsv does this 3× (date+time+timezone), l2ttln 2×, dynamic/xlsx 1× (no intra-row redundancy), tln `time` field is raw POSIX (no conversion), JSON family unaffected. **Entirely gated on a non-UTC output zone** — under the default UTC every `astimezone` branch is skipped and `_FormatTimeZone` returns `"UTC"` immediately, so the cost is zero by default. **Direction:** convert the instant to the target zone once per event and derive date/time/zone from that single value; detect fixed-offset zones; consider C-backed `zoneinfo` over pytz.

**D3 (opportunity #11). Windows EventLog lookups don't cache negative results.** CONFIRMED, medium. `GetMessageString`/`GetParameterString` store results only inside `if message_string:` (`winevt_rc.py:998,1038`); a miss caches nothing. On a miss, `_ReadEventMessageString` runs several `GetAttributeContainers(..., filter_expression=...)` calls (`:499-501,531-543`) that are **not** served by the lone `event_tag_per_event` index, i.e. full scans. Every event of a provider whose resources are absent (common on real images) re-runs the whole chain. **Scope corrected:** dynamic, l2t_csv, tln, json/json_line, xlsx, opensearch — **not** rawpy/kml (they never format a message field); data types are `windows:evt:record`/`windows:evtx:record`. **Direction:** cache negative lookups with a sentinel so a missing resource resolves at most once; resolve "provider has no usable message files" once per provider — turning O(unresolved events) into O(distinct keys).

**D4 (opportunity #12). JSON family re-serializes `path_spec` (and `date_time`) per event.** PLAUSIBLE, medium. `shared_json.GetFieldValues` (`shared_json.py:118-251`) serializes `event_data_stream.path_spec` via `WriteSerializedDict` every event (`:185-187`) — a nested parent-chain dict walk — and `date_time` (`:199-204`), plus a full per-attribute `GetFormattedField` loop. `path_spec` is typically identical across many consecutive events from the same source. **Scope corrected:** json_out/json_line fully; opensearch/opensearch_ts share only the path_spec serialization + dispatch (they drop `DateTimeValues`, `shared_opensearch.py:387-402`). The per-attribute dispatch is *not* the dominant cost — `GetFormattedField` runs a real callback for only 5 fields; others are a cheap getattr. **Direction:** memoize serialized `path_spec` per distinct `event_data_stream`; `date_time` memoization gives little (it varies per event).

**D5. Repeated `data_type.lower()` / `GetFormatStringAttributeNames` set rebuild / `_FormatExtraAttributes` set+sort.** CONFIRMED, low. `GetSourceMapping`/`GetMessageFormatter` lowercase per call (`mediator.py:323,347`); `GetFormatStringAttributeNames` returns a fresh `set(...)` each call (`interface.py:384,554`); l2t_csv `_FormatExtraAttributes` does one set alloc + in-place `.update` of ~25 reserved names + membership filter + `sorted()` per event (`l2t_csv.py:208-251`). Real but micro. **Direction:** cache lowercased→(formatter, source) mappings; return a precomputed frozenset; precompute the excluded-name set per data_type.

### Theme E — Output modules

**E1 (opportunity #7, cross-cutting). `--filter` applied only after full per-event materialization.** CONFIRMED, medium. `_ExportEvents` fetches `event_data` (`:278`), `event_data_stream` (`:284`), and resolves `event_tag` (`:292`) before `event_filter.Match` (`:297-300`). Content filters are Python-evaluated against decoded containers, never pushed to SQL; only the time-slice becomes a WHERE predicate (`sqlite_file.py:436-445`). A 1%-selective filter still decodes all N events. **Affects: all** (upstream of the output module). **Direction:** push cheaply-indexable predicates (and filters over event-row columns) into SQL so non-matching events are never materialized; reserve the Python `Match` for residual `event_data`-field predicates — decode then scales with matches.

**E2. Second in-module heap re-sort (`SortedStringHeap`) + formatted-string retention.** PLAUSIBLE, corrected to low. Sorted text modules push each formatted row onto a second heap keyed on a joined sort string, flushing on primary-key change or at 100000 (`text_file.py:10-59,205-239`). **Affects:** dynamic, l2t_csv, tln, l2ttln (SortedTextFileOutputModule/DSVOutputModule). **Correctness note, not pure overhead:** the engine heap orders same-timestamp events by `event_values_hash` (arbitrary for reading); the SortedStringHeap re-orders by *content* (dynamic: datetime+display_name+message; l2tcsv: time+filename+inode) — a genuinely different, deterministic ordering. Removing it changes output order, so the only valid fix is to fold the content tie-break key into the engine's `PsortEventHeap`. Memory is bounded to one same-timestamp cluster (or 100k), not the whole file.

**E3. XLSX per-cell column-width bookkeeping + 1,048,576-row limit.** PLAUSIBLE, corrected to low. `WriteFieldValues` does `len/min/max` per cell (`xlsx.py:235-253`) — the minimal correct incremental auto-width, negligible next to xlsxwriter's own per-cell dispatch. The real issue is a **correctness/scaling** one: a single worksheet (`:189-191`) with no rollover silently truncates timelines >~1.05M events in `constant_memory` mode. **Affects: xlsx only.** **Direction:** sample/heuristic widths; roll over to additional sheets or document the cap.

**E4. JSON `sort_keys=True` per event.** PLAUSIBLE, corrected to low. `json.dumps(field_values, sort_keys=True)` (`json_out.py:31`, `json_line.py:27`) sorts keys of each per-event dict. **Affects: json, json_line only** (repo-wide `sort_keys` grep = exactly these two). A constant-factor add-on over the pure-Python encode. **Direction:** emit insertion-ordered keys / build ordered dict.

**E5. OpenSearch bulk flush interval + two-pass dict build.** PLAUSIBLE, corrected to low. Default `_DEFAULT_FLUSH_INTERVAL = 1000` (`shared_opensearch.py:203`), already a single batched `bulk()` per 1000 docs (`:293-335`), user-tunable via `SetFlushInterval`; two-pass dict over ~10–30 fields. **Affects: opensearch, opensearch_ts only** (optional network modules, not the default CSV path). **Direction:** byte-sized/larger batches; single-pass document build; pipeline bulk sends.

### Theme F — Concurrency

**F1 (opportunity #2, the headline re-architecture). The whole decode+format loop is single-threaded though the dominant work is embarrassingly parallel.** CONFIRMED (concurrency, corrected critical→high). `_ExportEvents` runs the entire sequence — sorted-cursor pull → `GetAttributeContainerByIdentifier` → zlib.decompress (`sqlite_file.py:90`) → json.loads (`json_serializer.py:521`) → container rebuild → heap push → on flush, `GetFieldValues` (message/datetime/timezone) → write — on one thread (`output_engine.py:276-390`); `ExportEvents` starts only a status thread, no workers (`:645,650`). Only the final sort/dedup/MACB/write must stay serial for deterministic output; the decode/format stages that precede it are pure per-event functions. **Affects: all** for the decode half; message formatting only for message-bearing modules. **Direction:** parallel decode/format stage (tagged by order) + serial reassembly into `PsortEventHeap`.

**F2. SQLite read, CPU decode, and output write are serialized with no pipelining, despite independent cursors.** PLAUSIBLE, corrected to medium. Three different resources (disk/page-cache, CPU, output sink) run back-to-back and cannot overlap. acstore already uses a private cursor for `GetSortedEvents` (`sqlite_store.py:472-473`) separate from the by-index cursor, so a prefetch connection is a natural fit. Writes are actually buffered per-timestamp-group (`output_engine.py:209-213`), not strictly per-event. **Direction:** producer/consumer pipeline — a prefetch/decode stage on its own read connection streams ahead while format runs concurrently and an ordered queue drains to the writer.

**F3. zlib/SQLite release the GIL, so even a thread pool yields real speedup for decode.** PLAUSIBLE, medium. `zlib.decompress` (`sqlite_file.py:90`) and sqlite3 C calls release the GIL; today both run inline so the released-GIL windows are wasted. Only `json.loads`/`_ConvertJSONToValue` and formatting remain GIL-bound. **Direction:** offload the SELECT+decompress half of the lookup to a small thread pool returning decoded bytes/containers in order — true concurrency with the main thread's Python work, no process-pool IPC cost; escalate to a process pool where the JSON/format Python work dominates.

**F4. Formatting of survivors is parallelizable before the serial write.** CONFIRMED, medium. `GetFieldValues` (message template expansion, `astimezone`, winevt resource lookups) runs inline between heap-pop and write (`output_engine.py:452-459`). **Direction:** move `GetFieldValues` onto the parallel stage, leaving only `WriteFieldValues`/`WriteFieldValuesOfMACBGroup` + the within-timestamp `SortedStringHeap` serial; shared read-only state (message formatters, winevt LRU, timezone) must be made worker-safe or replicated per worker.

**F5. Engine is named `MultiProcess` and inherits the worker-pool/RPC framework but spawns no workers.** CONFIRMED, medium. `OutputAndFormattingMultiProcessEngine` subclasses `MultiProcessEngine` but never implements `_StartWorkerProcess` (`output_engine.py:112-116`, `# TODO: move this to a single process engine`); the extraction side already ships a working fan-out-with-merge (`task_engine`, `merge_helpers`, `zeromq_queue`). Single-threaded export is a design choice, not an infrastructure gap. **Direction:** reuse the extraction task-distribution + ordered-merge pattern for the output path.

**F6. Status-update thread — verified non-issue.** PLAUSIBLE, low. Wakes on a fixed 0.5s timer (`engine/engine.py:55`), ~2 wakeups/sec independent of throughput — no per-event GIL contention, negligible impact. Noted only because it is the sole concurrency actually present.

### Theme G — Memory & data structures

**G1 (opportunity #1, memory angle). 32K LRU too small and pathological for the random reference stream.** CONFIRMED (memory, high). Same root as A3/C1: `_MAXIMUM_CACHED_CONTAINERS = 32 * 1024` (`acstore/interface.py:236`, verified) over a uniform-random stream larger than the cache ⇒ hit rate collapses to `cache/working_set`, each miss paying SELECT + zlib + json + rebuild. **Conditional on distinct `event_data` > 32768** (smaller stores are fully cached). **Direction:** eliminate the random point lookup (ordered JOIN) rather than caching around it; a recency cache cannot exploit a random stream.

**G2. Full `EventObject` materialized with per-event `date_time` JSON deser even where unused.** PLAUSIBLE, corrected high→medium. Same code as C3. **Scope corrected:** true waste only for rawpy/null and narrow integer-time configs; most modules need the deserialized `date_time`. **Direction:** lightweight sort record (timestamp, desc, identifiers) + lazy `date_time`.

**G3. Full `EventData` rebuilt even when few fields are needed.** PLAUSIBLE, corrected high→medium. The premise "narrow modules read few fields" is mostly false: tln/l2t_csv/rawpy/dynamic(default)/json consume essentially the whole record via the message formatter / catch-all / extra-attributes. The real cost is the decode itself (C1), largely unavoidable given full-record consumption; field-projection would save little on the common path.

**G4 (opportunity #14, memory angle). All event tags held resident, string identifier allocated per event.** CONFIRMED, medium. `_GetEventTag` loads every `event_tag` into a dict keyed by `CopyToString()` and looks up `event.GetIdentifier().CopyToString()` per event (`output_engine.py:496-502`), building an `"event.<n>"` string from an integer per event even on untagged stores. **Affects: all.** **Direction:** key by the integer sequence number; short-circuit on untagged stores (eliminates N string allocations).

**G5. `CopyToDict` rebuilds a fresh attribute dict per event on top of the reconstructed container.** PLAUSIBLE, corrected to low. `dict(self.GetAttributes())` (`formatting_helper.py:332,360`, `containers/interface.py:90-96`) — one small dict per event (two for l2t_csv). Dwarfed by the following `FormatEventValues`. **Scope corrected:** rawpy/kml do **not** call it (no message field). **Direction:** reuse one `event_values` across message/message_short.

**G6. Cache-key f-string + `move_to_end` per lookup.** = C4 (low).

**G7. Repeated short strings (`data_type`, `_parser_chain`) not interned.** PLAUSIBLE, corrected to low. Overstated: `data_type`/`_parser_chain` live on `event_data`, served from the 32K LRU and shared, so not reallocated per event; only `timestamp_desc` (a tiny enum) is truly per-event. Live containers are bounded by the 32K cache + 100k heap, not "millions". **Direction:** minor; interning the small recurring set.

### Theme (orchestration, cross-cutting)

**O1 (opportunity #4). Two full event-table passes when analysis plugins are enabled.** CONFIRMED, high. `ProcessStorage` runs `_AnalyzeEvents` (`analysis_engine.py:122-137`) then the export phase (`output_engine.py:276-292`) sequentially against the same file with independent opens (`psort_tool.py:535-560`). Each calls `GetSortedEvents` (full un-indexed sort) and per-event `event_data`/`event_data_stream` fetches; caches are per-store and reset between phases, so no first-pass decode is reused. Doubles sort + N-blob-decode whenever ≥1 plugin is requested. **Affects: all**, only with analysis plugins (a plain run makes one pass). **Direction:** collapse analysis + export into a single ordered scan with plugin fan-out consuming the same stream the exporter formats.

**O2 (opportunity #2, orchestration view). Per-event single-row `event_data` fetch is the dominant unconditional cost of every run.** CONFIRMED, corrected critical→high. Restates C1 at the orchestration level: ~N `event_data` point lookups (+ up to N `event_data_stream`, which are cheap schema-row reads, not zlib+JSON) per run regardless of options, single-threaded, poor locality. Only mitigation present is the 32K LRU.

**O3. Analysis pass resolves tags with one indexed query per event vs the export pass's bulk cache.** PLAUSIBLE, low. `analysis_engine.py:137` calls `GetEventTagByEventIdentifier` per event → a fresh filtered query + `list()` (`reader.py:110-127`), while export bulk-loads once (`output_engine.py:496-502`). Indexed point lookup (not a scan), **analysis pass only**, not on the export hot path. **Direction:** reuse the export bulk-cache approach in analysis.

## 5. Cheap/safe wins vs. larger re-architecture

**Cheap / safe (low risk, byte-identical output, mostly storage- or micro-level):**
- **Add a persisted `event(timestamp)` (covering) index at finalize** — removes the full external sort and the pre-first-row stall (#3, A1). Highest cheap-win ROI.
- **Read-oriented PRAGMAs** on the psort connection: `temp_store=MEMORY`, large `cache_size`, `mmap_size` (#6, A4).
- **Parameter-bind the rowid** (`WHERE rowid = ?`) to restore statement-cache reuse (#13, A5).
- **Promote `_event_values_hash` + `timestamp_desc` to event-table columns** so dedup precedes blob hydration (#5, B1) — schema change but mechanically contained.
- **Per-event memoization in formatting:** render the message once for `desc`+`short` (#8, D1); convert the instant to the target zone once per event (#9, D2); cache the resolved formatter per data_type and reuse one `CopyToDict` (#10, C2); memoize serialized `path_spec` per `event_data_stream` (#12, D4).
- **Negative-result caching** for Windows EventLog resource lookups (#11, D3).
- **Short-circuit `_GetEventTag` on untagged stores; key caches by int/tuple not f-string** (#14/#15, C4/C5/G4).
- Drop JSON `sort_keys` (E4); XLSX sheet-rollover / documented cap (E3).

**Larger re-architecture (higher risk/reward, needs careful determinism handling):**
- **Single ordered `event ⋈ event_data` (+ `LEFT JOIN event_data_stream`) streaming scan** replacing N random point lookups (#1, C1/A2/A3) — makes the 32K LRU moot and restores sequential locality.
- **Producer/consumer pipeline parallelizing decode+format** behind a serial, order-preserving sort/dedup/MACB/write tail (#2, F1–F5) — the only path to order-of-magnitude throughput gains; thread pool first (GIL-releasing zlib/SQLite), process pool for JSON/format-bound work; reuse the extraction fan-out-with-merge.
- **Single ordered pass shared by analysis + export** (#4, O1).
- **Eliminate the per-timestamp heap** in favor of a pure streaming adjacency scan, contingent on B1 (hash as an event column) — folds the within-timestamp content ordering (E2) and `timestamp_desc` (B4) into one SQL-driven order.
- **Filter pushdown to SQL** so decode scales with matches, not total events (#7, E1).

## 6. Correctness caveats any speed change must preserve

1. **Deterministic, chronological output ordering.** Events must emerge in `timestamp` order, then by the engine's within-timestamp ordering. A timestamp index or JOIN preserves this; any parallel decode/format stage must reassemble results into the exact pre-change order before sort/dedup/write (tag each unit with `(timestamp, insertion index)`).
2. **Within-timestamp content ordering.** Sorted text modules impose a *content-based* secondary order via `SortedStringHeap` (dynamic: datetime+display_name+message; l2tcsv: time+filename+inode) that differs from the engine heap's `event_values_hash` order. Removing the second heap changes byte output unless its tie-break key is first moved into `PsortEventHeap`.
3. **Byte-identical output.** Field serialization, truncation (GetMessageShort's 80-char cut), JSON key order, and timezone/`dynamic_time` rendering must not change for a given input + options.
4. **Dedup semantics.** Adjacency dedup on `(timestamp_desc, event_values_hash)` with `deduplicate_events` defaulting True (`-a`/`--include-all` disables). `event_values_hash` must stay consistent with `CalculateEventValuesHash` if promoted to a column. Preserve — and ideally fix, not worsen — the latent mid-timestamp-flush split at `_HEAP_MAXIMUM_EVENTS=100000` (B2) where same-timestamp groups >100k lose cross-flush adjacency.
5. **MACB grouping.** Only l2t_csv collapses a MACB group into one line; other modules write members individually. Streaming/parallel changes must keep MACB members contiguous within their timestamp group.
6. **Time-slice semantics.** A `timestamp` index must still honor the `>=`/`<=` range filter and the `number_of_events_from_time_slice` accounting.
7. **`--filter` result equivalence.** SQL predicate pushdown must produce exactly the set the Python `event_filter.Match` would, with residual `event_data`-field predicates still evaluated in Python; `filter_limit` early-break behavior must be preserved.
